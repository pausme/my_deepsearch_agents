# 新房装修决策与预算管家开发任务拆分

## 1. 开发目标

基于当前 deepsearch-agents 项目，将通用深度研搜系统改造成面向 C 端用户的装修决策助手。

第一阶段目标：
- 用户可以创建装修分析会话。
- 用户可以上传报价单、合同、清单等资料。
- 系统可以围绕装修场景完成资料分析、联网检索和风险识别。
- 系统可以生成 Markdown/PDF 装修诊断报告。
- 前端可以展示分析过程、结果和文件下载入口。

## 3. P0 任务

### 3.1 场景 Prompt 改造

目标：
- 将系统从通用深度研搜改造成装修决策助手。

改动文件：
- `app/prompt/prompts.yml`
- `app/agent/subagents/*.py`

任务：
- 改造主智能体角色为“装修决策顾问”。
- 保留公开搜索、数据库、RAGFlow 三类助手。
- 新增报价单分析和合同风险分析的任务约束。
- 增加免责声明和价格范围表达规范。

验收标准：
- 用户输入装修需求时，系统优先围绕房屋、预算、材料、报价、合同展开。
- 报告不再输出泛泛的行业研究口吻。
- 涉及价格、合同、施工风险时有明确边界提示。

### 3.2 上传文件安全加固

目标：
- 避免文件名路径穿越、超大文件和不支持格式导致风险。

改动文件：
- `app/api/server.py`
- `app/tools/upload_file_read_tool.py`

任务：
- 增加文件名清洗。
- 限制文件后缀白名单：`.pdf`、`.docx`、`.xlsx`、`.xls`、`.md`、`.txt`。
- 增加单文件大小限制。
- 上传后保存文件元数据。
- 返回结构中增加文件类型和大小。

验收标准：
- 上传 `../a.txt` 不会写出会话目录。
- 上传不支持格式时返回明确错误。
- 上传超大文件时拒绝。
- 原始文件名和存储文件名可追踪。

### 3.3 报告模板改造

目标：
- 让输出从普通回答变成标准装修诊断报告。

改动文件：
- `app/tools/markdown_tools.py`
- `app/tools/pdf_tools.py`
- 可新增 `app/templates/renovation_report.md`

任务：
- 固定报告章节结构。
- 增加预算健康度、风险等级、报价问题、行动清单。
- 增加免责声明。
- 生成文件名使用会话编号和时间。

验收标准：
- Markdown 报告包含固定章节。
- PDF 能正常生成。
- 报告可以直接发给家人、设计师或工长阅读。

### 3.4 前端入口文案改造

目标：
- 让用户一进来就知道这是装修决策助手。

改动文件：
- `frontend/src/App.tsx`
- `frontend/src/components/*.tsx`
- `frontend/src/styles.css`

任务：
- 改造产品标题和说明。
- 增加装修场景快捷问题。
- 上传区文案改成报价单、合同、户型图说明、清单。
- 结果区改成装修诊断报告。

验收标准：
- 首屏表达清楚“装修决策与预算分析”。
- 用户能自然上传装修资料并发起分析。

## 4. P1 任务

### 4.1 装修会话模型

目标：
- 从单纯 thread_id 升级为业务会话。

新增文件建议：
- `app/domain/renovation.py`
- `app/api/renovation_schema.py`
- `app/api/renovation_server.py`

任务：
- 定义装修会话请求对象。
- 支持城市、面积、房型、预算、装修阶段、关注重点。
- 会话和 thread_id 绑定。

验收标准：
- 创建会话后可以提交多轮分析任务。
- 每个会话有独立文件目录和业务字段。

### 4.2 报价单分析助手

目标：
- 提供真正有业务价值的报价单风险识别。

新增文件建议：
- `app/agent/subagents/quote_review_agent.py`
- `app/tools/quote_tools.py`

任务：
- 解析 Excel 报价单。
- 标准化项目名称、单位、数量、单价、总价。
- 识别漏项、重复项、单位含混项、价格异常项。
- 输出结构化风险项。

验收标准：
- 至少识别 5 类报价风险。
- 能输出“问题、依据、影响、建议动作”。

### 4.3 合同风险助手

目标：
- 识别装修合同里的常见风险。

新增文件建议：
- `app/agent/subagents/contract_review_agent.py`
- `app/tools/contract_tools.py`

任务：
- 提取付款节点、工期、增项、材料替换、保修条款。
- 匹配风险规则。
- 输出合同风险项。

验收标准：
- 可以识别付款过度前置、工期责任不清、增项确认缺失等风险。
- 输出明确免责声明。

### 4.4 数据库只读安全改造

目标：
- 避免模型执行危险 SQL。

改动文件：
- `app/tools/db_tools.py`

任务：
- 只允许 SELECT/SHOW。
- 禁止 INSERT、UPDATE、DELETE、DROP、ALTER、TRUNCATE。
- 增加表名白名单。
- 增加默认 LIMIT。
- 查询结果脱敏。

验收标准：
- 危险 SQL 被拒绝。
- 未加 LIMIT 的查询自动限制行数。
- 非白名单表不可查询。

## 8. 开发注意事项

- 不要一开始就做完整账号体系，可以先预留用户 ID。
- 不要让模型直接操作任意 SQL。
- 不要让模型决定最终文件路径。
- 不要把合同分析包装成法律意见。
- 不要把价格范围说成精确报价。
- 不要为了产品化而破坏当前项目清晰的 Agent/Tool/API 分层。

## 9. 当前最小可执行里程碑

最小里程碑定义：
- 用户打开页面，看到装修助手。
- 上传一份 Excel 报价单。
- 输入“帮我分析这份报价单是否合理”。
- 系统展示分析过程。
- 系统输出报价风险清单。
- 系统生成一份装修报价诊断 PDF。

完成这个里程碑后，项目就从“通用 Agent 教学 Demo”变成了“有明确 C 端业务价值的装修决策产品原型”。
